# Bug Investigation: Fan Control Spins to 100% After Sleep (#2977)

## Session: 2026-02-24

### Status
completed

### Summary

After sleep/wake on Apple Silicon (M4 Max reported, likely affects all M-series), fans
incorrectly switch from automatic to manual mode. The user reports fans sometimes go to
100% speed, sometimes to minimum — consistent with entering manual mode without setting
a target RPM.

### Root Cause Analysis

**Primary Bug: `FanMode.auto3` treated as non-automatic in `resetModeAfterSleep` path**

On Apple Silicon, `thermalmonitord` controls fans using SMC mode value 3 (system mode).
The `FanMode` enum correctly defines this as `.auto3` with an `isAutomatic` helper, but
all comparisons use `== .automatic` / `!= .automatic` instead of `.isAutomatic`, causing
mode 3 to be misidentified as non-automatic.

### Bug Trace (step by step)

```
SETUP: Apple Silicon Mac, fans in auto mode, "save fans speed" OFF

1. App starts → loadFans() reads F%dMd from SMC
   - On Apple Silicon, thermalmonitord reports F%dMd = 3 (system mode)
   - FanMode(rawValue: 3) = .auto3  (NOT .automatic)
   - Fan is stored with mode = .auto3 in reader's sensor list
   - Reader NEVER updates mode after init (read() only updates RPM values)

2. Mac goes to sleep → sleepListener() fires
   - Guard: self.fan.customMode != .automatic
   - customMode is nil (never set) → nil != .automatic → true (guard passes!)
   - Saves willSleepMode = nil, willSleepSpeed = nil
   - Sets fan to auto mode, calls setMode(.automatic)
   - setMode(.automatic) callback persists customMode = .automatic

3. Mac wakes → wakeListener() fires
   - Sets resetModeAfterSleep = true
   - speedState is false → skips first block
   - customSpeed is nil → skips second block

4. Reader cycle runs → update(fan) called on FanView
   - fan.mode = .auto3 (from reader's list, never changed)
   - Line 928: self.resetModeAfterSleep && value.mode != .automatic
     → true && (.auto3 != .automatic)
     → true && true = TRUE  ← BUG TRIGGERS HERE

5. self.modeButtons?.setMode(.forced) is called
   → setMode(.forced) calls self.callback(.forced)
   → callback at line 656-661:
     - self.fan.mode = .forced
     - self.fan.customMode = .forced  ← PERSISTED TO USERDEFAULTS
     - SMCHelper.shared.setFanMode(fan.id, mode: 1)  ← WRITES TO SMC!

6. SMCHelper → XPC → Helper daemon → smc CLI → smc.swift:setFanMode(.forced)
   → unlockFanControl(fanId:)
   → Writes Ftst=1 (unlock thermalmonitord)
   → Waits 3 seconds
   → Writes F%dMd=1 (manual mode)
   → Fan is now in MANUAL mode with NO explicit target speed

7. Result: Fan runs at whatever F%dTg was (undefined after wake)
   - Sometimes max speed (firmware safety default)
   - Sometimes min speed (zero target residual)
   - Matches user report: "100% speed" and later "minimum speed"
```

### All Affected Code Locations

#### Bug 1 (PRIMARY): `popup.swift` line 928
```swift
// CURRENT (BUGGY):
if self.resetModeAfterSleep && value.mode != .automatic {
// SHOULD BE:
if self.resetModeAfterSleep && !value.mode.isAutomatic {
```
This is the trigger. `.auto3 != .automatic` evaluates to `true`, causing
`setMode(.forced)` which writes manual mode to SMC via the callback chain.

#### Bug 2: `popup.swift` line 881 (sleepListener guard)
```swift
// CURRENT (BUGGY):
guard SMCHelper.shared.isActive() && self.fan.customMode != .automatic else { return }
// SHOULD BE:
guard SMCHelper.shared.isActive(),
      let mode = self.fan.customMode, !mode.isAutomatic else { return }
```
When `customMode` is nil (user never set a mode), `nil != .automatic` = true in Swift.
This causes the sleep listener to run unnecessarily, writing to SMC and persisting
`customMode = .automatic` through the setMode(.automatic) callback. Not directly harmful
but contributes to state confusion.

#### Bug 3: `popup.swift` line 87 (checkFanModesAndResetFtst)
```swift
// CURRENT:
guard fanViews.allSatisfy({ $0.fan.mode == .automatic }) else { return }
// SHOULD BE:
guard fanViews.allSatisfy({ $0.fan.mode.isAutomatic }) else { return }
```
Won't reset Ftst when fans are in mode 3 (.auto3). Low severity since Ftst should
already be 0 when thermalmonitord is in control.

#### Bug 4: `popup.swift` line 871 (wakeListener second block)
```swift
// CURRENT:
if let value = self.fan.customSpeed, self.fan.mode != .automatic {
// SHOULD BE:
if let value = self.fan.customSpeed, !self.fan.mode.isAutomatic {
```

#### Bug 5: `popup.swift` line 1034 (ModeButtons init)
```swift
// CURRENT:
self.autoBtn.state = mode == .automatic ? .on : .off
// SHOULD BE:
self.autoBtn.state = mode.isAutomatic ? .on : .off
```
UI issue: if mode is .auto3, neither Auto nor Manual button is highlighted.

#### Bug 6: `main.swift` line 95 (termination handler)
```swift
// CURRENT:
if mode != .automatic {
// SHOULD BE:
if !mode.isAutomatic {
```

#### Bug 7: `popup.swift` line 858 (wakeListener speed restore)
```swift
// CURRENT:
if mode != .automatic {
// SHOULD BE:
if !mode.isAutomatic {
```

#### Design Issue: `FanMode.isAutomatic` exists but is never used
The `isAutomatic` property was added to `FanMode` (smc.swift line 51-53) but zero
call sites use it. Every comparison uses `== .automatic` or `!= .automatic`, defeating
the purpose of having `.auto3` in the enum.

#### Design Issue: Reader never updates fan mode after init
`SensorsReader.read()` only updates `.value` (RPM) for fans, never `.mode`. This means
the mode passed to `FanView.update()` is always the value from `loadFans()` at app
startup. If `F%dMd` returns 3 at startup (common on Apple Silicon), the reader
perpetually reports `.auto3`, triggering the bug on every wake.

### Why This Only Affects Apple Silicon (M3/M4 especially)

1. Intel Macs use `FS!` bitmask (values 0-3 with different semantics), not `F%dMd`
2. Apple Silicon `thermalmonitord` uses mode 3 (system control), a value that doesn't
   exist on Intel
3. M3/M4 have more aggressive thermal management, making mode 3 more prevalent
4. The `.auto3` enum case was added for Apple Silicon but comparisons were never updated

### Reproduction Steps

1. Install Stats 2.12.0 on Apple Silicon Mac (M4 Max confirmed)
2. Open Sensors popup, verify fans show "Automatic"
3. Sleep the Mac (Apple menu → Sleep or close lid)
4. Wake the Mac
5. Open Sensors popup immediately
6. Observe: fans show "Manual" mode, speed at 100% or near-minimum

### Empirical Findings (M4 Pro, macOS 15.5)

**Enum bug proven (investigations/prove-enum-bug.swift):**
- `FanMode.auto3 != .automatic` = true (the bug trigger) ← CONFIRMED
- `FanMode.isAutomatic` defined in smc.swift but zero uses in codebase ← CONFIRMED
- `nil != .automatic` = true in Swift (sleepListener guard bug) ← CONFIRMED
- `setMode(.forced)` triggers full SMC write chain, not just UI ← CONFIRMED

**SMC values on M4 Pro:**
- F0Md = 0.0, F1Md = 0.0 at rest (mode 0, not mode 3)
- Mode 3 not observed at rest on M4 Pro — may be specific to M4 Max or transient

**UserDefaults corruption found on test machine:**
- fan_0_mode = 1 (forced), fan_0_speed = 5354
- fan_1_mode = 1 (forced), fan_1_speed = 5533
- Sensors_speed = false (save fan speed NOT enabled)
- This shows the mechanism: customMode persisted as forced without user intent

**Regression confirmed via git history:**
- Before PR #2924 (v2.12.0): FanMode only had .automatic(0) and .forced(1)
- PR #2924 added .auto3(3) and .isAutomatic but did NOT update popup.swift comparisons
- Both user reports confirm "started happening on 2.12.0"
